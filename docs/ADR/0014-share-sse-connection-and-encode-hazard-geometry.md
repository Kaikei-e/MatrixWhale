# 0014: ブラウザー内のSSE接続を共有し、災害の座標を可逆符号化して配信する

## コンテキスト

ユーザー提供の `localhost.har` は47リクエスト、総転送量5,034,672 B。
災害SSEだけで1,961,949 Bを非圧縮転送し、地図ファイル4件は送信前に15.0〜19.5秒待機していた。
既存のHTTP/1.1配信では、警報・地震・災害がそれぞれEventSourceを開いていた。

## 決定

- `GET /api/v1/stream?geometry=polyline` に3種類のSSEをまとめる。
  イベント名は `alerts.*`、`earthquakes.*`、`hazards.*` とし、既存ストアへ振り分ける。
- 同じページのストアは参照数を管理して1本のEventSourceを共有する。
  最後の購読解除で接続を閉じ、再接続時は各一覧を取得し直す。
- バックエンドは3つのhubへの登録を終えてからHTTPヘッダーを送る。
  これによりクライアントのopen後の一覧取得と差分購読の順序を保証する。
- 単一のLast-Event-IDを別々のhubのカーソルとして使わない。
  再接続時は各チャネルのresyncで一覧を再検証する。
- 災害SSEの `primary_geometry` は、既存RESTと同じ可逆polyline形式を選択できる。
  符号化は購読者ごとではなく、1イベント・1表現につき1回だけ行う。
  ブラウザーはTimelineへ通知する前に元のGeoJSONへ復元する。
- 従来の個別SSEエンドポイントと通常GeoJSON形式を維持する。
- 初期一覧の取得中は大きい地図ファイルを待機させ、一覧取得の帯域を優先する。
  APIが応答しなくても地図が止まり続けないよう、待機には15秒の上限を設ける。

## 根拠（調査結果・出典）

[Chromiumのスケジューラー](https://chromium.googlesource.com/chromium/src/+/HEAD/services/network/resource_scheduler/resource_scheduler.cc)は、低優先度のリクエストを、高優先度の実行中リクエスト数と推定回線品質に応じて待機させる。
[3G以下のパラメーター](https://chromium.googlesource.com/chromium/src/+/HEAD/services/network/resource_scheduler/resource_scheduler_params_manager.cc)では、高優先度1件の重みが3、上限が8である。
このため、SSEが3本あるとソケットに空きがあっても低優先度取得が止まり得る。

Chromiumでネットワーク側の回線判定を3Gに固定し、下り1.6 Mbps・遅延150 ms・同一100 KBファイル2件で対照実験した。
3本のSSEではキュー待ちが15,011 / 15,014 ms、1本では両回とも約0.6 msだった。
回線判定を固定しない対照ではこの長い待機は生じなかった。
HARに実際の回線判定値は保存されていないため、ユーザーの判定値そのものを断定するものではない。

[WHATWGのSSE仕様](https://html.spec.whatwg.org/multipage/server-sent-events.html)は名前付きイベントと再接続時のLast-Event-IDを定義している。
計測手順と結果は [SSE性能レポート](../../perf/sse-network-2026-09-20.md) に記録する。

## 検討した代替案

- HTTP/2とTLSへの変更：有効だが配信構成の変更を伴い、SSE本文の転送量は減らない。
- 地図のpriorityだけ上げる：待機は回避できても、3本の常時接続と大きい災害本文が残る。
- SSEの全体gzip圧縮：既存の圧縮器は有限JSONボディ用であり、ストリームのflush制御を追加する必要がある。
- ポリゴンの頂点削除・座標丸め：元データの精度を変えるため採用しない。

## 影響とトレードオフ

ページあたりのSSE接続は3本から1本になる。
切断は全チャネルに影響するため、再接続とスナップショット再取得を共有する。
タブをまたぐSharedWorkerによる共有は導入しない。
大きい災害イベントによる共有接続内の転送待ちは残るが、可逆符号化で本文を削減する。
