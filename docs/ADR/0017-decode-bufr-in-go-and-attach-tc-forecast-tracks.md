# 0017: BUFRをGo内製パッケージでデコードし、熱帯低気圧進路予報をGDACS Hazardに紐付ける

## コンテキスト

[[0016]] において、WMO WIS2 Global Broker から MQTT v5 で電文を購読し、CAP 警報、熱帯低気圧（TC）進路予報（BUFR trajectory）、および地上観測値（BUFR SYNOP）を取り込む基本方針を決定した。

WMO の標準気象バイナリ形式である BUFR（Binary Universal Form for the Representation of meteorological data: Edition 3 および Edition 4）は、可変ビット長のビットストリーム、Table B（要素記述子）および Table D（合成記述子）による自己記述性、複雑な展開（expansion）・複製（replication）・演算子操作、圧縮サブセット（compressed data subsets）など高度な柔軟性と複雑性を備えている。
しかし、BUFR 電文を安全かつ効率的にデコードして本番システムで活用するためには、以下の技術的課題と制約を解決する必要がある。

- **ランタイムの安全性と依存性の排除**: 気象業界の標準参照実装である ECMWF ecCodes などの C 言語ライブラリを cgo 経由で使用する場合、クロスコンパイル環境の複雑化やメモリ安全性上の懸念が生じる。また Python サイドカーなどを導入すると、運用・保守の複雑化やプロセス間通信のオーバーヘッドが発生する。単一バイナリで安全に動作する軽量なデコード基盤が求められる。
- **非信頼入力に対するセキュリティ保護**: 公開 MQTT ブローカーから受信する外部バイナリ電文は非信頼入力（untrusted input）である。悪意ある細工電文や破損電文による無限ループ、再帰深度の爆発、メモリ枯渇攻撃などからプロセスを保護しなければならない。
- **配信元プロデューサーの実態への対応**: WIS2 経由のデータ配信においては、一部の配信センター（producer）が BUFR 電文を誤って GRIB とラベリングして配信する事例や、ダウンロードリンクへの高頻度アクセスに伴う HTTP 429（Rate Limit）の発生など、現実の運用環境特有のプロトコル不整合や接続制限に対処する必要がある。
- **多災害モデルおよび正準イベントとの整合性**: 各気象機関（ECMWF, JMA, NCEP 等）がバッチ実行サイクルごとに発行する熱帯低気圧のモデル進路予報を、[[0009]] で策定した多災害モデル（`sea.hazard`）および [[0005]] の canonical event 概念と矛盾なく統合し、GDACS の実況イベントと適切に突合・重畳表示する設計が求められる。

## 決定

1. **Go 内製パッケージ `wis2_adapter/app/bufr` による BUFR Edition 3/4 のデコード**:
   - ecCodes や cgo、Python サイドカーに依存せず、pure-Go で実装された内製デコーダーパッケージ `wis2_adapter/app/bufr` を導入する。
   - BUFR Edition 3 および Edition 4 の双方に対応する。
   - WMO 公式の BUFR4 v46 Table B（要素記述子）および Table D（合成記述子）の CSV ファイルをリポジトリ内に vendor 保持し、Go の `embed` 機能によりバイナリへ静的に埋め込む（ライセンスは MIT、出典元リファレンスを明記した `NOTICE` ファイルを同梱）。
   - WMO のマスターテーブルは後方互換性（backward compatibility）を維持して策定されているため、最新の v46 テーブルを用いることですべての過去バージョンの標準電文を正しくデコード可能とする。
   - 局所記述子（Local Descriptors: 組織独自のプライベート記述子）は非互換および解釈不一致の原因となるため、処理せず明示的に拒絶（reject / エラー）する。
   - 非信頼入力（untrusted input）に対する保護機構として、以下の制限・上限ガードを厳格に適用する:
     - メッセージサイズ上限（message size limit）
     - 記述子展開回数上限（expansion limit）
     - 複製反復回数上限（replication limit）
     - 再帰深度上限（recursion depth limit）
     - サブセット数上限（subsets limit）
   - 不正入力や境界条件によるパニックおよびリソース枯渇を防ぐため、Go 標準の Fuzz テスト（`go test -fuzz`）を常設して検証する。
   - デコーダーの正確性（correctness）は、実在する WIS2 電文（複数センターから得られた熱帯低気圧進路予報、および圧縮サブセットを含む SYNOP 地上観測データ）を用い、ecCodes で生成したゴールデンデータ（golden test fixtures）との完全一致テストによって固定（pin）する。ecCodes は本番システムでは一切使用せず、ゴールデンデータ生成用のオフライン検証ツールとしてのみ限定利用する。

2. **熱帯低気圧（TC）決定論的進路予報の取り込みと耐障害ダウンロード**:
   - 取り込み対象は決定論的進路予報（deterministic trajectory）のトピックに限定する（WMO BUFR テンプレート `3 16 082` に準拠）。アンサンブル予報（ensemble tracks）は対象外とする。
   - 電文から台風・サイクロン 1 台につき 1 つの Feature を抽出する:
     - 解析初期時刻（analysis time）
     - 予報ステップごとの中心位置（緯度・経度）
     - 中心気圧（MSLP: Mean Sea Level Pressure）
     - 最大風速（max wind）
     - 風配半径（wind radii）
   - ダウンロードリンクで宣言されたメディアタイプ（declared media type）は信頼せず無視する（一部のプロデューサーが BUFR 電文を GRIB と誤表記して配信しているため）。バイナリ先頭のマジックバイト（`BUFR`）を基準に判定する。
   - データ取得時にレートリミット（HTTP 429）が発生した場合は、指数バックオフ（exponential backoff）を伴うリトライを実施する。

3. **Core での履歴保持と GDACS 熱帯低気圧との突合（Matching）**:
   - コア側で受信したすべての計算実行ラン（run）を 7 日間保持する専用テーブル `sea.wis2_tc_track` を新設する。
   - 各実行ランを、現在アクティブな GDACS の熱帯低気圧（`sea.hazard` において `hazard_type = 'tropical_cyclone'` かつ `is_current = true`）と突合する。突合ロジックは Gleam の純粋ドメイン関数（`domain/`）として実装する:
     1. **台風・サイクロン名の正規化一致（normalized name match）**: 大文字小文字、空白、ハイフン、表記揺れを正規化して判定。
     2. **空間・時間近接一致**: 名前で一致しない場合、解析初期時刻（analysis time）における中心位置が GDACS サイクロン中心から距離 300 km 以内、かつ時刻が ±12 時間以内の場合に同一イベントと判定。
   - **GDACS 詳細パネルへの統合表示**:
     - GDACS ハザードに合致した実行ランは、GDACS ハザード詳細（`GET /api/v1/hazards/{source}/{source_id}`）の `forecast_tracks` フィールドとして提供する。
     - UI 表示においては、同一予報センター（centre）からは常に「最新の実行ラン（latest run per centre）」のみを重畳表示し、過去ランは描画しない。
   - **GDACS 未一致（Unmatched）イベントの独立ハザード化と番号擾乱の扱い**:
     - 名前が付与されている未一致の熱帯低気圧は、独立した新規ハザードとして `sea.hazard` に登録する（ソース: `wis2-<centre>`、優先度: 75。GDACS 実況値の 80 より低位。[[0016]] §2.6）。
     - 将来のバッチサイクルや GDACS 側の新規検知により当該熱帯低気圧が GDACS に一致した時点で、独立登録していた `wis2-<centre>` 側のハザードを終了（end / `is_current = false`）させ、UI 上の二重表示を防止する。
     - 名前が付与されていない番号擾乱（unnamed numbered disturbances）は、将来の解析や検証のため `sea.wis2_tc_track` に保存は行うが、`sea.hazard` への登録および UI 上の表示は行わない。
   - **風配半径（Wind Radii）の表現**:
     - 各ステップの風配半径（風速閾値・象限ごとの半径数値）はデータベースに保持し、詳細パネル上で数値として表示する。地図上でのポリゴン描画（drawing）は行わない。

4. **正準イベント（Canonical Events）モデルとの関係性**:
   - 地震における正準イベント（[[0005]] の `sea.event`）は複数観測網の震源決定を結合する主キー体系であるが、熱帯低気圧の進路予報は `sea.event` ではなく [[0009]] で確立された多災害モデル（`sea.hazard`）の GDACS ハザードに直接紐付ける（attach）。
   - これにより、観測実況・公式アラート（GDACS）と数値予報モデルによる進路予測（WIS2）という性質の違いを自然に表現し、[[0009]] のスキーマ・API 設計と完全な整合性を維持する。

## 根拠（調査結果・出典）

- **定性的・構造的事実**:
  - ※公開リポジトリの運用方針に基づき、実測値やトラフィック件数などの定量的数値は含めず、構造的事実および仕様上の事実のみを記録する。
  - WMO BUFR4 マスターテーブルは後方互換性を保証しており、最新版（v46）の Table B/D を用いることで過去の Edition 4 バージョンで作成された電文の全標準記述子を矛盾なく展開できる仕様であることが確認されている。
  - WIS2 配信環境において、特定の配信センターが BUFR バイナリ電文を格納した WNM メッセージの `media_type` プロパティに誤って `application/x-grib` 等の誤った MIME Type を設定して配信するケースが構造的に観察された。
  - 高頻度またはバッチダウンロード時に配信元サーバーから HTTP 429（Too Many Requests）が返却される事例が確認され、バックオフリトライが必要であることが判明した。
  - WMO BUFR テンプレート `3 16 082`（熱帯低気圧進路予報の標準シーケンス）は、予報時刻ステップごとの位置（緯度・経度）、中心示度（気圧）、最大持続風速、および各風速域の象限別風配半径を標準記述子の反復として体系的に定義している。
  - ecCodes は C 言語で書かれた業界標準の参照実装であるが、テストフィクスチャ生成用のオフライン環境でのみ利用し、ゴールデンテストによって Go 実装とのデコード一致性を証明できる。

## 検討した代替案

- **cgo 経由での ecCodes 利用（ecCodes via cgo）**:
  - 不採用。C 言語ライブラリとの cgo バインディングはクロスコンパイルの容易性を損ない、ビルド時間とコンテナイメージサイズを増大させる。また C 側のメモリリークやセグメンテーション違反（SEGV）が Go プロセス全体を巻き込んで異常終了させるリスクがある。
- **bufr_dump サブプロセスの呼び出し（bufr_dump subprocess）**:
  - 不採用。電文ごとに外部プロセス（`bufr_dump`）を `os/exec` で起動して標準出力を受け取る方式は、プロセス生成のオーバーヘッドが大きく、スループットとレイテンシの観点で著しく不利である。ゾンビプロセス管理やリソースリークの運用リスクも伴う。
- **Python サイドカーによるデコード（Python sidecar）**:
  - 不採用。Python ランタイムを別コンテナで動かし gRPC や HTTP で通信する構成は、コンテナ運用の複雑化、プロセス間通信のオーバーヘッド、依存パッケージの脆弱性管理コストを伴う。Go 単一バイナリによる自己完結型のアプローチが運用品質に優れる。
- **バージョン別テーブルセットの個別保持（per-version table sets）**:
  - 不採用。WMO BUFR の過去すべてのバージョン（v13〜v45 等）の Table B/D をそれぞれ個別に保持・ロードする方式は、vendoring コード・データ量の肥大化を招く。WMO マスターテーブルの後方互換性仕様により最新の v46 単一セットで過去電文の全標準記述子をデコード可能なため、不要な複雑性を排除した。
- **アンサンブル進路予報の取り込み（ensemble tracks）**:
  - 不採用。決定論的進路予報に対して、数十メンバーにおよぶアンサンブル予報（ensemble tracks）はデータ量が極めて大きく、ネットワーク帯域およびデータベース容量を激しく消費する。また、地図 UI 上に数十本の進路スパゲッティを描画することは画面の視認性を著しく損ねる（UI clutter）。まずは最も重要度の高い決定論的進路（テンプレート `3 16 082`）に絞る。
- **過去の全実行ランの UI 表示（showing all past runs）**:
  - 不採用。過去 7 日間に計算されたすべてのモデル実行ラン（1日複数回×複数センター）を UI 上に同時表示すると、進路が交差・重複して最新の予測状況が把握困難になる。過去ランは検証・監査用として DB に 7 日間保持しつつ、UI 上は各センターの「最新ランのみ」を選択的に重畳表示する。
- **風配半径のポリゴン描画（drawing wind radii）**:
  - 不採用。各ステップごとの 4 象限の風配半径（北東・南東・南西・北西の距離）を滑らかなポリゴンとして地図上に描画することは、サイクロン移動に伴う形状変形や重なり、レンダリング負荷が過大となる割に直感的な理解に寄与しにくい。GDACS の既存コーン表示との重複も生じる。風配半径は詳細パネル内の数値データとして提供し、地図のクリーンさを保つ。

## 影響とトレードオフ

- **得るもの**:
  - Pure-Go 実装による高速・安全で外部ランタイム非依存の BUFR Edition 3/4 デコーダー。コンテナ環境の軽量性とビルドの再現性を維持。
  - WMO BUFR4 v46 テーブルの静的埋め込みと入力制限・ファジングによる高いセキュリティと堅牢性。
  - ecCodes によるゴールデンテスト生成により、参照実装と同等のデコード精度を担保。
  - GDACS 熱帯低気圧と各国の最新モデル予測進路（ECMWF, JMA 等）の重畳表示が実現し、災害監視の精度と付加価値が向上。
  - 誤った MIME Type や 429 レート制限への耐性を備えた堅牢なインジェストパイプライン。
- **失うもの・引き受けるリスク**:
  - 局所記述子（Local Descriptors）を拒絶するため、一部の組織が独自拡張した非標準電文は破棄される（標準規格準拠を強制）。
  - アンサンブル予報を対象外としたため、予測の不確実性（確率的広がり）の可視化は将来の課題となる。
  - 純粋関数による名前・距離・時間でのマッチングを採用しているため、命名前の擾乱や急変時に GDACS との紐付けが一時的に未一致ハザードとして扱われる可能性（ただし後続サイクルで解消可能）。
  - テーブル更新（将来の WMO BUFR 新版リリース時）には Go コード内の vendored CSV 更新と再ビルドが必要。
